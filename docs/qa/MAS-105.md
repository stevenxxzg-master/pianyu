# MAS-105 Responsive and Accessibility Audit

Date: 2026-03-11

## Scope

Validated the current M5 web surfaces at desktop, laptop, and narrow mobile widths, then ran a baseline keyboard and axe-core accessibility smoke.

## Environment

- App runtime: local Rails + Vite stack on `http://127.0.0.1:3101`
- Alternate ports were used because host ports `3000`, `3036`, and `4000` were already occupied
- Repo-pinned runtimes: Ruby `3.4.8`, Node `24.14.0`
- Authenticated audit account: `admin@localhost`

## Breakpoints

- `1440x1200` wide desktop
- `1280x960` laptop
- `390x844` narrow mobile

## Audited routes

- Public: `/about`, `/explore`
- Authenticated: `/home`, `/notifications`, `/@showcase_account`, `/@admin/116209729468370793`, `/settings/preferences/appearance`
- Profile editing note: `/profile/edit` currently redirects to `/home` in this repo state, so settings validation used the exposed preferences flow instead

## Responsive result

- No major layout breakage or horizontal overflow was observed on the audited routes at `1440`, `1280`, or `390` widths
- Mobile navigation, profile header, status detail, notifications list, and settings form remained usable in the audited flows
- DOM overflow smoke returned `overflow=0` for the core audited routes across all three target widths

## Keyboard smoke

- `Tab` reaches skip links first on the app shell, then moves into header actions and primary content actions
- Home timeline focus order remained usable through skip links, column header buttons, status container, status meta links, and reply action
- Notifications focus order exposed a real semantic issue: focus lands on the whole notification card and then enters inner links inside the same interactive container

## Accessibility findings

### High-priority follow-up issues

1. `MAS-108` - feed semantics and nested interactive controls
   - `div.item-list[role="feed"]` contains direct `button[tabindex]` children on `/home`, `/notifications`, and `/@showcase_account`
   - `/notifications` nests interactive controls inside `div[role="button"][tabindex="0"]`
   - `@showcase_account` avatar link is focusable without a discernible accessible name

2. `MAS-109` - About page skip-link target and empty links
   - `/about` exposes a "skip to main content" link but does not render `#skip-link-target-content-1`
   - `/about` has no `main` landmark in the audited DOM
   - When contact metadata is empty, `/about` still renders empty focusable links such as `mailto:` and an `@undefined` admin placeholder

## Validation evidence

- Responsive DOM smoke:
  - `desktop:about/home/explore/profile_showcase/status_admin/notifications -> overflow=0`
  - `laptop:about/home/explore/profile_showcase/status_admin/notifications -> overflow=0`
  - `mobile:about/home/explore/profile_showcase/status_admin/notifications -> overflow=0`
- axe-core smoke at `390x844`:
  - `/about` -> `link-name`
  - `/home` -> `aria-required-children`
  - `/notifications` -> `aria-required-children`, `nested-interactive`
  - `/@showcase_account` -> `aria-required-children`, `link-name`
  - `/explore` and `/@admin/116209729468370793` -> no wcag2a/wcag2aa violations in this smoke run

## Conclusion

The audited M5 pages are broadly stable across the target desktop and mobile widths, but MAS-105 should track two high-priority accessibility follow-ups before considering the redesign fully accepted for baseline accessibility.
